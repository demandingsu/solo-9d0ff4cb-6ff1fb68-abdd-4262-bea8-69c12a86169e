# 隧道夜间试跑：通行时长样本服务

把同一轮夜间试跑的**入口雷达**与**出口雷达** CSV 记录配对成可信的通行时长样本。
两台雷达没有共享车号，因此通过时间关系推断一对一配对。

## 规则

* 每份 CSV 最多 12 条观测，必须包含观测号列与 UTC 整分钟时间列。
* 入口→出口间隔（秒）必须落在 **180～480 秒（3～8 分钟，含端点）**。
* 一对一配对的目标按字典序：
  1. 先使行程数**最多**；
  2. 再使 `Σ|通行时长 − 5 分钟|` **最小**。
* 只有出现在**所有**最优配对中的行程才会作为 `confirmed_trips` 交付。
  其余观测进入 `pending_observations`，`reason` 为：
  * `ambiguous_pairing`：该观测参与了其它等价最优配对，对象无法唯一确定；
  * `no_optimal_pair`：该观测不属于任何最优配对（时间窗内无对象，或已被更优配对排除）。
* `optimal_pairings` 给出最优配对的等价方案总数，便于判断结果可靠程度。

实现使用精确的位掩码动态规划（每个 CSV ≤12 条，状态数 ≤ 13·2¹²），
不是贪心或启发式：先求出最优值，再精确统计每个可行配对出现在多少个最优解中，
计数等于最优解总数者才算“所有最优配对中都存在”。

## 启动

```bash
docker compose up --build -d
```

服务监听 `http://localhost:8000`，交互文档与上传表单见 <http://localhost:8000/docs>。
数据保存在命名卷 `trips-data` 的 SQLite 数据库中。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/docs` | Swagger UI，可直接上传与查询 |
| POST | `/api/rounds` | multipart 上传 `entry_file`、`exit_file`，整版替换 |
| GET | `/api/rounds/current` | 当前版本的行程、待核观测与汇总 |
| GET | `/api/trips` | 当前版本已确认行程 |
| GET | `/api/pending` | 当前版本待核观测 |
| GET | `/api/rounds/current/verification` | 只读核验当前轮次（见下） |
| GET | `/healthz` | 健康检查 |

上传示例：

```bash
curl -F 'entry_file=@sample-data/entry.csv;type=text/csv' \
     -F 'exit_file=@sample-data/exit.csv;type=text/csv' \
     http://localhost:8000/api/rounds
```

### CSV 格式

```csv
observation_id,utc_minute
E001,2026-11-15T22:00:00Z
E002,2026-11-15T22:01:00Z
```

* 表头可识别 `observation_id` / `id` / `观测号` 等，时间列可识别
  `utc_minute` / `time` / `观测时间` 等；多余列会被忽略。
* 时间必须是 UTC 整分钟（`Z` 或 `+00:00`，秒必须为 `00`），也接受 `YYYY-MM-DD HH:MM`。
* 重复观测号、空文件、超过 12 行、非 UTF-8 文件等都会被拒绝（HTTP 422），
  错误信息逐行给出。

## 一致性与整版替换

* 每次成功上传都会在**一个写事务**里先删除旧版本、再写入新版本
  （`rounds` → `observations` / `trips` 外键级联）。
* 文件校验失败（422）不会写出任何数据；写入失败（500）会回滚事务，
  旧版本完整保留，响应明确说明“已保留上一版结果”。
* 读取端每条请求开启一个 SQLite 读事务；数据库强制 WAL 模式
  （无法启用则拒绝启动），因此并发读取只会看到完整的旧版本或完整的新版本，
  绝不会混合两个版本的行程与待核观测。

## 交付前只读核验

数仓交付通行时长样本前，质控员可调用
`GET /api/rounds/current/verification` 对**当前已提交轮次**做独立核验。
该端点不写任何数据，核验所需的全部内容（含入库时保存的两份原始 CSV
BLOB）在**同一个 SQLite 读事务快照**内读出；即使核验期间发生上传整版替换，
报告也完整对应所读取的那一个轮次，响应中的 `version` 标明被核验轮次。

核验步骤：

1. 对库内两份原始 CSV BLOB 重新计算 SHA-256 与字节数，与入库时记录的摘要对照；
2. 用上传时同一套严格解析器重新解析两份文件；
3. 用同一个精确配对引擎重新配对；
4. 将重算结果与入库的观测（含状态与待核原因）、已确认行程（含时长与偏差）、
   汇总统计逐项对照。

结论 `status` 三选一：

| status | 含义 | `deliverable` |
| --- | --- | --- |
| `verified` | 摘要一致、解析成功、所有对照字段完全相符，可交付 | `true` |
| `mismatch` | 原始文件可核实，但重算结果与入库内容存在差异，**不可交付** | `false` |
| `unverifiable` | 原始文件摘要不符或文件无法解析（或无法重新配对），**无法核实**；不能依据库内行程判定可信，此时不输出字段差异作为证据 | `false` |

响应还包含：

* `digest_checks`：entry/exit 各自的记录摘要与实算摘要、字节数及是否相符；
* `parse_errors`：重新解析原始文件时的逐行错误（无错误为空列表）；
* `differences`：逐项差异，每条给出 `scope`（`observation` / `trip` /
  `summary`）、`field`、重算期望值 `expected`、入库实际值 `actual`，
  适用时标出 `observation_id`（观测号）或 `entry_id`/`exit_id`（行程号）。

```bash
curl http://localhost:8000/api/rounds/current/verification
```

## 测试

```bash
pip install -r requirements-dev.txt
pytest -q
```

测试覆盖：配对边界（3/8 分钟含端点）、多解歧义、行程数优先于代价、
与暴力枚举的随机差分对比（30 组固定种子）、CSV 校验各类错误、上传失败保留旧版、
整版替换、真实 SQL 故障回滚、并发读取不混版本；以及只读核验的
摘要相符/不符（含记录摘要与 BLOB 两类篡改）、字节数不符、文件无法解析、
观测状态与待核原因差异、行程缺失与字段差异、汇总差异（均标注观测号或行程号）、
核验期间并发替换时报告始终对应单一已提交轮次。

开发时另用 3000+ 组随机与边界样本、以及多进程读写压测与暴力枚举做过差分核对，
均未发现不一致（这些脚本未纳入仓库测试集）。

## 已知边界

* 观测时间精度为整分钟，因此 `duration` 与 `deviation` 均以 60 秒为粒度。
* 入口与出口是各自独立的观测号命名空间，两侧即使出现相同编号也不会互相冲突；
  每条待核观测在响应里带有 `radar` 字段以区分来源。
* 12×12 全可行且多解时最慢约 1 秒（精确计数所有最优解）。
* 只保留当前版本：成功上传会替换上一版，旧版本不提供历史查询接口。
